## Daftar temuan

### 15. TINGGI, R-32, 14 halaman non-dashboard tanpa h1

Hanya `/admin` yang punya `h1` ("Dashboard bendahara"). Seluruh halaman lain
memakai `h2.page-title` sebagai judul: `/`, `/login`, `/ganti-password`,
`/admin/*` (11 rute), `/warga/*`. Struktur heading benar (satu `h1` brand di
header + satu `h2` konten), tetapi `h1` konten tidak ada sehingga screen reader
tidak mendapat judul halaman yang diprioritaskan. C-4: keyboard-only lolos
(urutan Tab benar, skip link ada), tetapi landmark judul lemah.

Alasan satu baris: judul konten memakai `h2` di 14 rute, `h1` hanya di dashboard.

Perbaikan: naikkan judul konten tiap halaman menjadi `h1` (class `page-title`
tetap, hanya tag berubah), kecuali dashboard yang sudah benar. Brand di header
sudah `p.brand` (bukan heading), jadi tidak ada konflik h1 ganda.

### 16. TINGGI, R-03, tombol `.btn-sm` 38px di desktop

Terukur di browser nyata: "Atur sekarang" 133x38, "Lihat detail" 114x38,
"Kelola" 82x38, filter pembayaran 87-114x38 di viewport 1280/1024/768. Di
mobile (360/390) media query menaikkan ke 44px sehingga `smallN:0`. WCAG 2.5.8
memberi pengecualian untuk kontrol yang punya padanan, tetapi R-03 proyek
menuntut 44px dan audit-003 butir 13 sudah mencatat alasan "mouse presisi"
hanya di komentar, bukan keputusan teruji. Tablet 768 dengan sentuh (iPad)
mendapat 38px karena breakpoint 640px: jempol di tablet kecil tetap kesulitan.

Alasan satu baris: 38px di bawah ambang 44px R-03 untuk semua pointer kasar.

Perbaikan (pilih satu): (a) naikkan `.btn-sm` ke 44px di semua viewport
(satu baris CSS, tabel sedikit lebih tinggi); (b) gunakan media
`(pointer:coarse)` sebagai pemicu 44px, bukan lebar viewport, sehingga iPad
sentuh dapat 44px dan desktop mouse tetap 38px. Opsi (b) presisi, opsi (a)
boring dan aman.

### 17. SEDANG, tabel non-tunggakan tanpa caption dan scope

Dashboard tunggakan sudah benar (caption + `scope="col"` + wrapClass). Tabel
lain belum: `/` (scope 3, tanpa caption), `/admin/houses` (scope 6, tanpa
caption), `/admin/audit` (scope 6, tanpa caption), `/admin/payments/pending`
dan `/admin/payments` (scope 0 sepenuhnya: header tanpa scope, tanpa caption).
Fungsi `table()` sudah mendukung `options`, tetapi pemanggil lama tidak
mengirimnya. Dampak: screen reader membaca sel tanpa konteks kolom di 5 tabel.

Alasan satu baris: 5 pemanggil `table()` belum mengirim `caption`.

Perbaikan: tambahkan `{ caption: '...' }` di tiap pemanggil tabel
(papan publik, pending, payments, houses, audit, expenses, reports). Satu baris
per tabel, tanpa perubahan visual.

### 18. SEDANG, filter pembayaran tanpa grup dan label

Empat link filter ("Semua/Menunggu/Diverifikasi/Ditolak") di `/admin/payments`
adalah `div` berisi anchor tanpa `role="group"`, tanpa `aria-label`, dan tanpa
penanda aktif selain class visual (`btn-primary` vs `btn-ghost`). Screen reader
tidak tahu ini satu kelompok filter dan mana yang aktif. Terukur: `smallN:4`
di desktop hanya soal tinggi 38px (lihat 16), fungsi keyboard normal.

Alasan satu baris: kelompok filter tanpa semantik grup dan status aktif.

Perbaikan: bungkus dengan `<div role="group" aria-label="Filter status
pembayaran">` dan tambah `aria-current="true"` pada filter aktif. Dua baris
markup.

### 19. RENDAH, checkbox 13px dihitung sebagai input <16px iOS

Audit font input iOS 390: semua text/date/month/file/select 16px (lolos
auto-zoom), satu-satunya `smallN:1` adalah `input[type=checkbox]` 13.33px
(default browser). Ini false positive: checkbox bukan kolom ketik, Safari tidak
melakukan auto-zoom padanya. Tidak ada perbaikan visual yang dibutuhkan, tetapi
alat ukur dan dokumentasi harus mencatat pengecualian agar temuan tidak
diangkat ulang tiap audit.

Alasan satu baris: checkbox bukan pemicu auto-zoom, tetapi alat ukur
menyamakannya dengan kolom ketik.

Perbaikan: tidak ada perubahan kode; catat di `follow-up-004` sebagai bukan
temuan. (Dimasukkan sebagai nomor agar terlacak, bukan agar diperbaiki.)

### 20. RENDAH, R-31, alasan 38px vs pointer-kasar belum tertulis

Butir 13 audit-003 meminta satu baris alasan di README ("mouse presisi").
Temuan 16 di atas menunjukkan alasan itu tidak cukup (tablet sentuh). Keputusan
final (opsi a atau b) beserta alasannya harus tertulis di README bagian Arah
desain, menggantikan butir lama bila opsi berubah.

Alasan satu baris: dokumentasi keputusan belum mencerminkan kasus tablet.

Perbaikan: satu-dua baris README setelah opsi 16 dipilih.
